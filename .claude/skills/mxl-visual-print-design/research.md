# Исследовательская выжимка: дизайнерские печатные формы 1С / MXL

Дата фиксации: 2026-09-20.

Цель: превратить разработку печатной формы по SVG/PNG/PDF-эталону из «подгонки глазами» в воспроизводимый инженерный процесс с реальным runtime-доказательством.

## 1. Что подтверждает сама платформа 1С

### Табличный документ — нативная основа печатных форм

Официальная документация 1С описывает `ТабличныйДокумент` как объект встроенного языка для создания выходных документов, включая первичные документы и отчеты. Редактор табличного документа является инструментом разработки печатных форм.

Источники:
- https://v8.1c.ru/platforma/tablichnyy-dokument/
- https://v8.1c.ru/platforma/redaktor-tablichnogo-dokumenta/

Практический вывод: дизайнерскую ВПФ следует строить как нативный MXL/`ТабличныйДокумент`, а не пытаться считать SVG/HTML/CSS готовой моделью печати 1С.

### Именованные области — штатный механизм декомпозиции

Официальный редактор поддерживает именованные области: отдельные ячейки и группы ячеек, включая вложенные области. Он также поддерживает графические объекты и картинки.

Источник:
- https://v8.1c.ru/platforma/redaktor-tablichnogo-dokumenta/

Практический вывод: сложную форму удобно строить и проверять смысловыми областями/блоками. Это дает стабильные точки для заполнения данных, повторяемых строк и блочного visual regression.

### Параметры страницы реально влияют на печать

В руководстве пользователя 1С отдельно описаны параметры печати табличного документа: поля, колонтитулы, масштаб, режим «по ширине страницы», ориентация и другие параметры. Масштаб печати не равен масштабу просмотра в редакторе; режим «по ширине страницы» автоматически подбирает масштаб.

Источник:
- https://v8.1c.ru/upload/static/instrukciya-po-ehkspluatacii-v8.pdf

Практический вывод: сравнение только с тем, что видно в редакторе MXL, ненадежно. Неожиданный fit-to-page способен сделать геометрически неверный макет визуально «почти подходящим» либо, наоборот, разрушить правильно рассчитанные размеры. Формат бумаги, поля и масштаб должны быть частью layout spec и runtime evidence.

### Длинный текст и высота строки

Стандарты разработки 1С рекомендуют при формировании печатных форм с табличными макетами использовать `АвтоВысотаСтроки = Истина` для строк, где длинный текст иначе может быть обрезан из-за недостаточной ширины колонок.

Там же отдельно указано, что не следует задавать заведомо нереалистичные поля страницы, в частности нулевые поля; поля меняют, когда это действительно регламентировано формой.

Источник:
- https://its.1c.ru/db/content/v8std/src/1%C2%A0200/i8100548.htm

Практический вывод: clipping и переносы — не косметика. Они должны проверяться на реальном runtime-выводе с реальными строками данных. Авто-высота применяется осознанно: там, где динамический текст должен расширять строку, а не разрушать фиксированную дизайнерскую геометрию.

### Постраничная компоновка должна проверяться платформой

Методическая поддержка 1С описывает `ТабличныйДокумент.ПроверитьВывод()`: метод проверяет, поместится ли набор областей на текущей странице, и учитывает настройки печати документа.

Источник:
- https://its.1c.ru/db/content/metod8dev/src/developers/platform/metod/spreadsheet/i8102226.htm

Практический вывод: для составных блоков, итогов, подписей и таблиц нельзя надежно решать вопрос разрыва страницы только количеством строк. При необходимости следует опираться на штатную проверку вывода с реальными настройками печати.

## 2. Главный инженерный вывод исследования

Надежная последовательность для reference-driven формы:

**A4 → физическая геометрия в мм → layout spec → native MXL → реальная команда печати 1С → PDF → фиксированный PNG → crop блока → visual gate → fresh review → Owner PASS.**

Почему именно так:

1. SVG/PNG содержит пиксельную геометрию конкретного эталона, а печать 1С живет в физической странице, параметрах `ТабличныйДокумент` и реальном механизме печати.
2. MXL — табличная модель, а не browser layout engine. Прямое копирование CSS/SVG-координат не дает гарантии одинакового результата.
3. Финальный перенос текста, высота строк, масштаб и разбиение по страницам проявляются именно при реальном выводе.
4. PDF фиксирует то, что реально собирается печатать/сохранять пользователь.
5. Растеризация PDF в одинаковом размере дает сопоставимую систему координат для автоматического визуального контроля.
6. Блочная итерация локализует ошибки и не позволяет «сломать низ страницы, исправляя шапку».

## 3. Единицы измерения: чего нельзя делать

Не вводить в код непроверенные магические коэффициенты «пиксель → MXL». В проекте должны существовать две явные системы:

- **эталонная** — пиксели SVG/PNG при зафиксированном размере canvas;
- **физическая** — миллиметры страницы, полей и смысловых блоков.

Если эталон соответствует полной странице известного физического размера, координаты блоков нормализуются относительно ширины/высоты страницы. Затем MXL настраивается по физической геометрии и проверяется обратной связью через runtime PDF.

Это важнее попытки вывести универсальный коэффициент ширины MXL: шрифты, объединения, печатный масштаб, renderer и содержимое могут влиять на конечный результат.

## 4. SoT и layout spec должны быть раздельными

**Visual SoT** отвечает на вопрос «как должно выглядеть».

**Layout spec** отвечает на вопрос «какая физическая геометрия должна получиться» и содержит:
- формат/ориентацию бумаги;
- поля;
- общий content bbox;
- bbox каждого блока;
- ключевые выравнивания;
- размеры/позиции изображений;
- допустимые переносы и динамические зоны;
- правила перехода между страницами.

MXL — реализация spec, но не источник истины для spec.

## 5. Почему static/MXL PASS недостаточно

Проверка XML/MXL может подтвердить:
- существование областей;
- структуру макета;
- параметры/имена;
- отсутствие части синтаксических ошибок.

Она не доказывает, что пользователь получит правильную страницу после:
- загрузки EPF/CFE;
- выполнения настоящей команды печати;
- заполнения реальными данными;
- вычисления высоты строк;
- применения полей/масштаба;
- экспорта в PDF.

Поэтому уровни приемки должны быть разделены:

`STATIC/FAST PASS` → `RUNTIME CONTENT PASS` → `VISUAL PASS` → `OWNER PASS`.

Ни один предыдущий уровень не подразумевает следующий.

## 6. Детерминированный visual gate

Для каждого проверяемого состояния фиксируются:
- один и тот же candidate SHA;
- один и тот же fixture/order;
- одна и та же тестовая база/платформа;
- один и тот же способ экспорта PDF;
- одна и та же растеризация (DPI/размер страницы);
- одна и та же область crop;
- одна и та же версия SoT/layout spec.

Минимальные автоматические проверки:
- размеры страницы;
- внешний bbox контента;
- геометрия блока;
- clipping;
- лишние переносы;
- положение картинок;
- линии/заливки;
- масштаб;
- page break;
- image diff с ограниченными допусками к антиалиасингу.

Для текста полезно различать **геометрическую ошибку** и небольшое различие растрирования шрифта. Допуск к рендерингу не должен превращаться в допуск к сдвигу блока.

## 7. Evidence должен быть неизменяемым и SHA-bound

Минимальный пакет:
- candidate SHA;
- идентификатор SoT/layout spec и их hash;
- fixture/order ID;
- runtime environment;
- PDF + hash;
- page PNG + hash;
- crop измененного блока + hash;
- результаты gate/метрики;
- статус статических/runtime проверок.

Нельзя считать evidence валидным, если:
- PDF сделан от другого SHA;
- картинка вручную исправлена после печати;
- вместо runtime PDF используется screenshot редактора;
- fixture изменился между candidate/reference без фиксации;
- результат невозможно повторить.

## 8. Реальные строки важнее визуального сходства

Эталон дизайна может показывать условные 8 строк, но тестовый заказ может содержать 2. Нельзя добавлять фиктивные позиции ради визуального совпадения.

Правильная проверка:
- реальное количество строк остается реальным;
- динамические области сравниваются по правилам layout spec;
- статические блоки сравниваются с эталоном напрямую;
- для regression при необходимости используется отдельно утвержденный deterministic fixture, но он не маскируется под реальные данные.

## 9. Блочная стратегия для сложной формы

Если документ визуально насыщенный, вводится последовательность блоков `B1..Bn`.

Для каждого блока:
1. зафиксировать bbox/spec;
2. изменить только этот блок;
3. сформировать runtime PDF;
4. получить page PNG + crop;
5. прогнать visual gate;
6. fresh reviewer проверяет evidence;
7. при Owner-gated процессе получить Owner PASS;
8. только затем открывать следующий блок.

Эта схема уменьшает область поиска ошибки и предотвращает бесконтрольную переработку всей страницы.

## 10. Что не работает и почему

### «Подгоним MXL на глаз»
Не воспроизводится и плохо локализует ошибки.

### «Совпадает в редакторе — значит печать совпадет»
Не учитывает реальную команду печати, данные, масштаб и разбиение.

### «Сделаем один огромный визуальный diff всей страницы»
Полезно как финальная проверка, но плохо как цикл разработки: неизвестно, какой блок породил изменение, особенно при динамической таблице.

### «Нарисуем недостающие строки, чтобы screenshot совпал»
Создает ложное доказательство и не тестирует продукт.

### «Растянем candidate/reference до одного размера перед сравнением»
Маскирует ошибку масштаба — одну из главных ошибок печатной формы.

### «После печати чуть поправим PDF/PNG»
Доказательство перестает подтверждать результат 1С.

## 11. Применение к Teplovik Agent KP

Для текущего КП агента проект уже имеет visual SoT/layout spec. Методика означает:
- A4 portrait и утвержденные поля являются входом, а не результатом ручного подбора;
- блоки B1–B5 принимаются последовательно;
- B1 не дает права автоматически менять B2–B5;
- runtime только на разрешенной dev-базе;
- данные заказа не подделываются под референс;
- на review идет реальный PDF, page PNG и crop текущего блока от exact SHA;
- технический/Nadzor PASS не заменяет визуальный Owner PASS.

## 12. Граница источников

Официальные материалы 1С подтверждают возможности и ограничения `ТабличныйДокумент`, параметры страницы, именованные области, авто-высоту и проверку постраничного вывода.

Последовательность `SoT → физическая геометрия → runtime PDF → deterministic visual gate → SHA-bound evidence` является инженерной методикой проекта, выведенной из этих ограничений и опыта regression/debugging. Она намеренно строже минимальных требований платформы 1С.
