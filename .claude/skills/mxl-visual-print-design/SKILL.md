# /mxl-visual-print-design — дизайнерская печатная форма 1С по эталону

Этот skill дополняет обычные `mxl-*`/`epf-*` проверки. Компиляция макета, наличие именованных областей и корректные данные — необходимые, но недостаточные условия. Для дизайнерской формы источником истины является **реальный результат печати 1С**.

## Обязательная цепочка

**A4 → мм → MXL → runtime PDF → deterministic PNG/crop → visual gate → fresh review → Owner PASS**

Нельзя заменять эту цепочку сравнением XML/MXL, скриншотом редактора или субъективным «похоже».

## Входные данные

До изменения макета зафиксируй:
- visual SoT: утвержденный SVG/PNG/PDF;
- физический формат страницы и ориентацию;
- поля печати в миллиметрах;
- layout spec: блоки и их bbox/размеры/отступы;
- реальные данные/детерминированный fixture для runtime;
- candidate SHA, к которому будет привязано доказательство;
- разрешенный scope задачи.

Если этих данных нет, сначала сформируй layout spec; не подгоняй MXL «на глаз».

## 1. Нормализация эталона в физическую геометрию

1. Зафиксируй размер бумаги (например A4 = 210×297 мм) и ориентацию.
2. Зафиксируй поля печати в мм.
3. Переведи координаты визуального эталона в физическую модель страницы: content bbox, ширины колонок, высоты блоков, интервалы, размеры изображений.
4. Раздели страницу на именованные смысловые блоки (`B1`, `B2`, ...), если форма сложная.
5. Pixel-координаты эталона используются как средство измерения, а не как единицы MXL. Не переноси CSS/SVG-модель буквально в табличный документ.

## 2. Построение нативного MXL

- Используй именованные области для логических блоков и повторяемых строк.
- Управляй ширинами, высотами, объединениями, границами, заливками, шрифтами и картинками средствами `ТабличныйДокумент`/MXL.
- Для длинного динамического текста предусматривай корректную авто-высоту строк, когда это допустимо макетом.
- Учитывай реальные настройки печати: размер бумаги, ориентацию, поля, масштаб и режим «по ширине страницы».
- Не компенсируй ошибочную геометрию случайным масштабом печати.
- Для разрыва страниц и составных блоков используй возможности проверки вывода/постраничной компоновки, а не предположение по числу строк.

## 3. Итерация только через реальный runtime

После минимальной правки:
1. FAST: структура/MXL/EPF/регистрация/статические проверки.
2. Выполни реальную печатную команду в разрешенной тестовой базе.
3. Получи настоящий `ТабличныйДокумент` из того же пути, которым пользуется пользователь.
4. Выгрузи PDF непосредственно из runtime-результата.
5. Растеризуй страницу детерминированно в PNG с фиксированными DPI/размером.
6. Сделай crop изменяемого блока по layout spec.
7. Сравни candidate с SoT в одинаковом масштабе.
8. Исправляй только обнаруженное отклонение и повторяй цикл тем же warm Coder.

**FAST ≠ FINAL. Static PASS ≠ Runtime PASS. Runtime content PASS ≠ Visual PASS.**

## 4. Что обязан проверять visual gate

Минимум:
- формат/ориентация страницы;
- поля и общий content bbox;
- положение и размер блока;
- горизонтальный и вертикальный масштаб;
- clipping/выход за границы;
- неожиданные переносы строк и изменение числа строк;
- шрифт, кегль, насыщенность и межстрочная геометрия в пределах доступной автоматической проверки;
- границы, заливки, разделители;
- размеры и позиции картинок;
- ширины колонок и высоты строк;
- переходы на следующую страницу;
- отсутствие незапланированного fit-to-page/масштабирования.

Автоматический diff может иметь обоснованные допуски к антиалиасингу/рендерингу шрифтов, но допуск не должен скрывать геометрическое смещение.

## 5. Блочная приемка

Для сложной формы двигайся блоками. Следующий блок нельзя начинать, если задача/Owner требует приемку предыдущего.

На каждом блоке:
- candidate runtime PDF;
- page PNG;
- crop блока;
- эталонный crop/координаты;
- visual gate результат;
- fresh independent review;
- при Owner-gated задаче — явный Owner PASS.

Не улучшай соседние блоки «заодно».

## 6. Реальные данные обязательны

Нельзя:
- дорисовывать отсутствующие строки ради сходства с эталоном;
- подменять номенклатуру, суммы или реквизиты фиктивными данными без явно утвержденного fixture;
- вручную редактировать PDF/PNG после 1С;
- показывать screenshot вместо доказательства runtime-печати;
- собирать evidence от другого SHA.

Если в эталоне 8 строк, а в реальном заказе 2 — форма должна содержать 2 реальные строки. Сравнивай геометрию тех элементов, которые действительно присутствуют.

## 7. FINAL evidence

FINAL пакет должен быть привязан к **точному candidate SHA** и содержать минимум:
- candidate SHA;
- SoT/layout-spec идентификатор или hash;
- fixture/order ID;
- runtime environment;
- PASS/FAIL статических и runtime-проверок;
- исходный PDF и hash;
- page PNG и hash;
- crop измененного блока и hash;
- visual-gate результат/метрики;
- подтверждение, что доказательства сформированы именно из этого SHA.

Evidence без SHA-binding или с ручной постобработкой недействителен.

## 8. Красные флаги

Остановись и исправь процесс, если видишь:
- «в MXL выглядит правильно, значит готово»;
- визуальную приемку только по XML/скриншоту редактора;
- свободное масштабирование reference/candidate перед сравнением;
- смену fixture между итерациями без причины;
- одновременную правку нескольких блоков при block-gated задаче;
- расширение runtime-скрипта в универсальный framework вместо детерминированного пути печати;
- технический PASS, объявленный Owner/Visual PASS;
- доказательство без exact SHA.
