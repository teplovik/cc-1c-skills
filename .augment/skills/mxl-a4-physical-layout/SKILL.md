# /mxl-a4-physical-layout — A4 image/SVG → mm → MXL → runtime visual gate

Цель: переносить утвержденный дизайнерский эталон в 1С не «на глаз» и не подбором случайных ширин колонок, а через явную физическую систему координат страницы и замкнутый цикл измерения реального PDF.

Перед работой прочитай `reference.md`. Там разделены **OFFICIAL 1C**, **EMPIRICAL** и **PROJECT POLICY**.

## Обязательный конвейер

`SoT image/SVG/PDF → physical page contract → anchor map in mm → MXL → REAL 1C runtime PDF → raster → anchor measurements → SELF_VISUAL_GATE → adjust → repeat`

MXL/XML сам по себе **не является доказательством визуального совпадения**.

## 1. Зафиксируй reference frame

До правки MXL запиши:
- формат бумаги и ориентацию;
- размер полного эталонного растра `Wpx × Hpx`;
- что именно представляет растр: **full physical page**, printable area или content crop;
- поля печати в мм;
- `PrintScale/МасштабПечати`, `FitToPage/АвтоМасштаб`;
- DPI, если он известен и имеет смысл;
- шрифты/окружение, влияющие на переносы текста.

Если координатная система неизвестна или противоречива — `BLOCKED_SOT_GEOMETRY`; не компенсируй конфликт случайными MXL offset'ами.

## 2. Переведи full-page raster в физические координаты

Для A4 portrait: `210 × 297 mm`.

Если канонический растр изображает **весь лист A4**:

```text
sx = 210 / Wpx   mm/px
sy = 297 / Hpx   mm/px

x_mm = x_px * sx
y_mm = y_px * sy
w_mm = w_px * sx
h_mm = h_px * sy
```

Не хардкодь конкретное разрешение. `1191×1684` — только пример. Сначала проверь aspect ratio и reference frame.

Для изображения с достоверным DPI:

```text
width_mm  = px_x / DPI_x * 25.4
height_mm = px_y / DPI_y * 25.4
```

Не смешивай DPI-derived размеры изображения с page-derived координатами, пока системы координат явно не согласованы.

## 3. Построй machine-readable geometry map

До реализации зафиксируй для значимых anchor'ов:

```text
name, x_mm, y_mm, w_mm, h_mm,
left/right/top/bottom behavior,
clip_expected,
tolerance_mm / tolerance_px
```

Минимум для дизайнерской шапки: content bounds, logo, slogan/right block, service line, boundary следующего блока. Для остального документа добавляй title, requisites, table, total, footer/ad blocks.

Фиксированная графика может использовать физическую геометрию рисунков там, где API 1С это поддерживает. Динамические товары, количества, цены и бизнес-текст должны оставаться настоящими MXL-областями/ячейками, а не «запечатываться» в картинку.

## 4. Не считай ширину MXL миллиметрами напрямую

Официально высота строки — пункты, ширина колонки — условные «средние символы»; поэтому `ШиринаКолонки=10` не означает 10 мм.

Для вертикали:

```text
1 typographic point = 25.4 / 72 = 0.352777... mm
pt = mm * 72 / 25.4
```

Практическое исследование сообщества получило для MXL:
- вертикаль: `1 ≈ 0.3528 mm`;
- горизонталь: `1 ≈ 1.8522 mm` (`5.25 pt`).

Это **EMPIRICAL calibration seed**, не официальный универсальный контракт. Финальная истина — измеренный runtime PDF в целевой платформе/окружении.

## 5. Предпочитай однородную сетку

Для дизайнерских форм вместо десятков произвольных форматов строк/колонок используй стабильную fine grid и объединяй клетки в более крупные области.

Практические варианты из исследования:
- `width=2`, `height=10.5` → около `80×55` ячеек на A4, удобно для шрифтов примерно 6–9;
- более точная сетка `width=1`, `height=5.25` → около `160×110`.

Это стартовые схемы. Размер printable area, поля и конкретный макет должны рассчитываться отдельно. Не создавай тысячи объединений без необходимости; учитывай официальную рекомендацию не усложнять SpreadsheetDocument чрезмерным количеством колонок/merged cells.

## 6. Проверяй SoT на физические противоречия

Пример: full-page A4 raster `1191×1684` дает примерно `0.1763 mm/px`. Тогда anchor `x=33 px` ≈ `5.82 mm`, `y=35 px` ≈ `6.17 mm`, а поле `7 mm` соответствует примерно `39.7 px`.

Если одновременно объявлены «поле ровно 7 мм» и «контент начинается ровно в 33 px от физического края», оба требования не могут быть точными в одной системе координат. Зафиксируй конфликт и выбери/получи один SoT. Не лечи это скрытым масштабированием.

## 7. Запрет скрытого масштабирования

Для pixel/physical-accurate задач явно контролируй:
- размер страницы;
- поля;
- `FitToPage/АвтоМасштаб`;
- масштаб печати;
- горизонтальный overflow;
- переносы текста и AutoHeight;
- clipping у края страницы.

Если 1С уменьшила лист из-за переполнения по ширине, это visual FAIL, даже если отдельный X-anchor случайно совпал.

## 8. Замкнутый runtime loop

После каждой содержательной геометрической правки:
1. собрать/загрузить на разрешенную test IB;
2. сформировать форму реальным кодом 1С на реальном fixture/document;
3. записать PDF;
4. растрировать с фиксированным scale/DPI;
5. измерить anchor'ы;
6. сравнить с canonical geometry map;
7. исправить только причинные размеры/offset'ы;
8. повторять до machine visual PASS.

Не отдавай Owner промежуточные FAIL-рендеры.

## 9. Visual gate

Обязательные проверки для каждого объявленного anchor:
- `dx`, `dy`, `dw`, `dh`;
- left/right/top/bottom;
- expected clipping/right-edge behavior;
- layout scale/overflow;
- отдельный residual/perceptual compare, допускающий raster/font antialiasing noise, но **не** маскирующий геометрический сдвиг через автоматическое выравнивание.

Known-bad fixtures обязаны FAIL. Canonical-vs-canonical обязан PASS.

`MANUAL`, missing или FAIL по обязательной визуальной геометрии не может давать `NADZOR_PASS`/`OWNER_REVIEW_READY`.

## 10. Acceptance artifact

Для дизайнерской ВПФ/ПФ единственный визуально авторитетный результат — **реальный runtime PDF, сформированный 1С на точном tested SHA**, плюс page PNG/crop и машинные метрики сравнения.

Статический MXL PASS, compile PASS или красивый SVG-макет не заменяют runtime visual PASS.

## Failure modes

Остановись и исправь причину при:
- full-page raster перепутан с content crop;
- DPI metadata принята за page coordinate system без проверки;
- SoT anchors конфликтуют с физическими полями;
- MXL column width ошибочно трактуется как mm;
- `FitToPage`/overflow незаметно изменяет масштаб;
- логотип/картинка сохраняет пропорции, но имеет неверный bbox;
- шрифт заменен, изменились wrap/line-height;
- правый блок должен клиппиться у края, но целиком помещается (или наоборот);
- comparator проверяет только Y/общий bbox и пропускает X/W/clip;
- результат проверен только в редакторе MXL, а не в PDF из 1С.

## Связанные навыки

Совмещай с `mxl-info`, `mxl-compile`/`mxl-validate`, EPF/CFE skill'ами и проектными runtime/print-acceptance gates. Этот skill задает **геометрическую методику**, а не заменяет сборку, BSP-регистрацию или бизнес-проверки.
